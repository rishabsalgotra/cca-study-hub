Harness engineering: the system around the model

The model proposes; the harness disposes. A harness is all the code and configuration around an LLM: the loop that calls it, the context it sees, the tools it may use, the permissions that gate them, the checks that verify its work, and the traces that tell you what happened. With the same model, the harness often decides whether an agent is a toy or a teammate. This page builds one up, from concepts to a tested ~200-line implementation.

1. What is a harness?

The one-line definitionAgent = Model + Harness. The model is the engine. The harness is everything else that makes it a car you can trust on a road: steering (the loop), fuel (context), controls (tools), brakes (permissions and budgets), dashboard (traces), and inspection (verification and evals).

Why harness engineering matters

  • The same model gives very different results in different harnesses. Agent benchmark scores depend heavily on the scaffold: the tools offered, how errors are reported, and when the agent is allowed to stop.
  • Reliability lives in the harness. Budgets, approvals, sandboxes, and verification are code. The model can't promise them.
  • Cost and latency live in the harness. Caching, context hygiene, and model routing are harness decisions.
  • Harnesses are what you can change today. You can't retrain the model, but you can ship a better harness this afternoon.

3. The control loop: when to call, continue, and stop

ConcernGood practice
Stop conditionsFinish on end_turn after verification; stop on refusal; continue on max_tokens (or raise it); resend on pause_turn (server tools).
BudgetsCap turns, output tokens, dollars, and wall-clock time. All are hard stops in code. A model-visible task budget (beta task_budget) lets the model pace itself instead of being cut off.
Warn before cutting offA few turns before the limit, append a short instruction ("3 turns left, wrap up") so the run ends with a summary instead of mid-edit.
RetriesThe SDKs already retry 408/409/429/5xx and connection errors with backoff (2 retries by default). Add your own retry only around tools, and only for idempotent ones.
Loop detectionNotice the same tool called with the same arguments repeatedly, and intervene (a message, or a stop).
Streaming & long turnsStream large outputs to avoid HTTP timeouts. Show progress, and let users interrupt.

4. Context assembly, caching and append-only transcripts

Every request re-sends the whole conversation, and the API processes it as one long prefix: tools → system → messages. Prompt caching makes the unchanged part of that prefix cheap and fast. That leads to the most important context rule in harness engineering: keep the past byte-for-byte stable and only append.

Rules for the context builder

  1. Freeze the prefixTools in a deterministic order, a system prompt with no timestamps or request IDs, and memory files loaded once per session.
  2. Append, never rewriteDon't edit or delete earlier messages. Beyond caching, newer models bind their thinking blocks to the exact conversation that produced them. Editing history invalidates them (and new API accounts get a 400 for it).
  3. Mid-session instructions as messagesTo change instructions, append a {"role": "system", …} message instead of editing the top-level system prompt. It preserves the cache and carries operator authority.
  4. Shrink with server-side toolsUse API compaction (compact_20260112) or context editing (clear_tool_uses_20250919) rather than hand-rewriting history. Cap tool output before it is appended.
  5. MeasureLog usage.cache_read_input_tokens. If it stays at zero, something in your prefix changes every request.

5. Permissions, hooks and sandboxing

Safety in a harness is layered, so no single mistake is catastrophic.

1 · Prompt

Tells the model the rules. Soft: it guides most behaviour, but it can be forgotten or overridden by injected text.

2 · Permissions

Allow / ask / deny per tool or command pattern, checked by code before execution.

3 · Hooks

Your scripts run at lifecycle events and can block, modify, or add context. Deterministic.

4 · Sandbox

Even if everything above fails, the process can't reach what it isn't given: files, network, credentials.

6. Verification: don't accept "done" without proof

The highest-leverage thing a harness can do is give the agent a way to check its own work, and refuse to finish until the check passes. Models are good at fixing a failure they can see.

VerifierStrengthWatch out for
Rules / code (tests, linters, type-checkers, schema validation)Fast, cheap, objectiveOnly as good as the tests; agents may "fix" tests instead of code, so protect test files
Visual (screenshots of UI)Catches layout and rendering bugsNeeds a browser tool and a clear spec
LLM as judge (a separate reviewer with a rubric)Handles fuzzy quality (tone, completeness)Costs tokens; calibrate against human grades
Human reviewThe final authority for high-stakes changesSlow; save it for what matters

9. Long-running agents: work that spans many context windows

Some jobs (building an app, a large migration) can't finish in one context window. Each new session starts with no memory, so the harness must make the environment carry the state:

  1. Initializer sessionSets up the project, writes a structured feature list (all items "failing"), an init.sh to start the app, and a progress file, then makes the first git commit.
  2. Each working session starts by orientingRead the progress file and git log, run init.sh, and run a smoke test to confirm nothing is broken before starting.
  3. One feature at a timePick the highest-priority failing item, implement it, and verify it end to end.
  4. Leave a clean stateMark the item passing only after verification, commit with a descriptive message, and update the progress notes for the next session.
# features.json (the agent may only flip "passes"; never delete or edit tests)
[{"id": "auth-01", "description": "User can sign up with email", "passes": true},
 {"id": "auth-02", "description": "Password reset email is sent", "passes": false}]

# progress.md (written at the end of every session)
## Session 14
- Done: auth-01 (signup), verified in browser; commit 3f2a91c
- Next: auth-02. Mail sender stub exists in src/mail.ts
- Gotcha: run `npm run db:reset` before e2e tests
💡 Why JSON for the feature list?Structured files are harder for the model to "accidentally" rewrite than prose, and easy for the harness to check (e.g. a hook that rejects edits removing items).

11. Evaluating a harness

Every harness change (new tool description, different compaction threshold, new hook) can help one task and hurt another. Treat the harness like any other software: a fixed task set, automatic graders, and a number you track.

  1. Collect tasksReal requests with a checkable outcome (tests that must pass, expected fields, a rubric). Start with 20–50; grow from production failures.
  2. Grade automaticallyCode checks first; LLM judges with a rubric for fuzzy quality; humans to calibrate the judges.
  3. Run each task several timesAgents are stochastic. One run tells you little.
  4. Change one thing at a timeAn ablation shows which harness component actually moved the score.
  5. Read transcripts of failuresThe fix is usually visible: a misleading tool description, a missing error message, a context flood.

🎯 pass@k vs pass^kpass@k: at least one of k tries succeeds. That's fine when a human picks the best attempt. pass^k: all k tries succeed. That's what matters for an unattended agent that runs every day. A harness with 60% per-try success has pass@3 ≈ 94% but pass^3 ≈ 22%.

12. Anti-patterns checklist

Anti-patternDo instead
Safety rules only in the promptPermissions + hooks + sandbox; the prompt explains why
Timestamps or per-request data in the system promptFrozen prefix; volatile data in the latest message
Editing or deleting earlier messagesAppend-only; server-side compaction and context editing; role: "system" messages for new instructions
Raising exceptions on tool failureis_error results with actionable text
Unbounded loopsTurn, token, dollar, and time budgets, plus a warning before the cut-off
Accepting "done" at face valueVerification on end_turn; Stop hooks
Dumping whole files or results into contextCaps, pagination, just-in-time reads, subagents
Judging changes from one lucky runRepeated trials; pass^k; ablations
bypassPermissions on a laptop with real credentialsOnly in disposable, network-restricted sandboxes

Self-check quiz

Score: 0 / 0 answered

1 · Your team requires that every edited file is auto-formatted. What's the most reliable implementation in Claude Code?
B. Hooks are deterministic and run every time. Instructions are followed most of the time, which isn't a guarantee.
2 · Cache reads stay at zero across requests in a long session. Most likely cause?
C. Caching is a prefix match. Any byte change invalidates everything after it, so a changing system prompt or tool order silently kills the cache.
3 · Mid-session, you need to tell the agent "the deploy freeze is now active." What's the best harness technique?
A. Appending keeps the cached prefix (and thinking blocks) valid and carries operator authority. Editing or deleting history breaks both.
4 · A Stop hook runs tests and exits 2 on failure. Users report the agent sometimes never stops. Fix?
D. The hook should block once and then let the agent stop (reporting the failure) rather than loop indefinitely.
5 · In the Agent SDK you added "Write" to allowed_tools and wrote a can_use_tool callback to block writes outside the repo. Writes outside the repo still happen. Why?
B. Remove Write from allowed_tools (or enforce the rule in a PreToolUse hook, which runs regardless).
6 · An agent passes a task 60% of the time per run. For an unattended nightly job, which metric best reflects the risk?
C. Consistency matters when no human picks the best attempt. pass^k measures reliability; pass@k measures "can it ever do it".
7 · A multi-day build agent keeps redoing finished work in each new session. Best harness fix?
A. New sessions start with no memory, so the harness must make the environment carry the state.
8 · Which change belongs in the harness rather than the model prompt?
D. Output caps and redaction must happen every time, before the model sees the data, so they're code. The others are guidance.
