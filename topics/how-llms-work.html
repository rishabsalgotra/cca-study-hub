Topic 2 · Foundations

How LLMs work: from your text to the model's reply

Follow a single prompt through the whole pipeline: text becomes tokens, tokens become vectors, vectors pass through dozens of transformer layers, and a probability distribution produces the next token. That step repeats until the model stops. Once you see the pipeline, things like token limits, temperature, prompt caching, stop_reason and "lost in the middle" make sense.

Why it matters explains cost, latency, limits & failure modes ≈ 45–60 min read

1. The journey at a glance

Every request to Claude (or any decoder-only LLM) goes through these stages. The rest of the page explains each one.

  1. Assemble the promptSystem prompt, tool definitions, and the conversation history are formatted into one long text sequence with role markers.
  2. TokenizeThe text is split into sub-word pieces (tokens), and each piece is mapped to an integer ID from a fixed vocabulary.
  3. EmbedEach token ID looks up a row in the embedding matrix and becomes a vector of thousands of numbers.
  4. Add positionPosition information is mixed in (e.g. RoPE), so the model knows token order.
  5. Transformer layers (×N)Each layer runs self-attention (tokens exchange information) and then an MLP (per-token processing), with residual connections. The vectors become richer at each layer.
  6. Unembed → logitsThe final vector at the last position is projected to one score per vocabulary token.
  7. Softmax + samplingTemperature, top-k and top-p shape the probabilities, and one token is picked.
  8. Repeat (autoregression)The new token is appended and the model runs again for the next one. A KV cache avoids recomputing earlier tokens.
  9. StopGeneration ends on an end-of-turn token, a stop sequence, max_tokens, or a tool call. That reason is the API's stop_reason.
  10. Detokenize & streamToken IDs are turned back into text and streamed to you, or parsed into structured blocks such as tool_use.
One sentence to rememberAn LLM is a function that takes a sequence of tokens and returns a probability distribution over the next token. Everything else (chat, tool use, reasoning) comes from calling that function repeatedly.

2. Step 1 — Assembling the prompt (chat template)

The model doesn't receive "a message". It receives one flat sequence. The API turns your structured request (system prompt, tools, messages[]) into that sequence using a chat template: special marker tokens that separate roles and turns.

# What you send (Messages API)
system: "You are a concise geography tutor."
messages: [ {role: "user", content: "What is the capital of France?"} ]

# Conceptually, what the model sees (marker names are illustrative)
<system>You are a concise geography tutor.</system>
<user>What is the capital of France?</user>
<assistant>          ← the model continues writing from here
  • Tool definitions (name, description, JSON schema) are serialised into the prompt too. That's why tool descriptions use up tokens and strongly influence which tool is picked.
  • The model is stateless. It has no memory between API calls. Every request resends the entire conversation, including earlier tool results. "Memory" features (CLAUDE.md, conversation history) work by putting text back into the prompt.
  • Prefill: if you end with a partial assistant message, the model simply continues it. That's because generation is just "continue this sequence".
🎯 Why this mattersLong conversations get more expensive and slower every turn, because the whole history is reprocessed. Hence context management, compaction, and prompt caching.

3. Step 2 — Tokenization: text → token IDs

Neural networks process numbers, not characters. A tokenizer splits text into tokens (frequent sub-word chunks) and maps each one to an integer token ID in a fixed vocabulary.

Worked example

The text The capital of France is through the public GPT-2 tokenizer (Claude uses its own tokenizer with different IDs, but the idea is identical):

The464 capital3139 of286 France4881 is318

Notice the leading space is part of the token (" capital"), and common words are a single token. Rare words get split: something like "tokenization" might become "token" + "ization", and an unusual name might become several fragments.

How the vocabulary is built: Byte-Pair Encoding (BPE)

  1. Start with the 256 possible bytes (UTF-8), so any text, emoji, or language can be represented. Nothing is ever "unknown".
  2. Count the most frequent adjacent pair in a huge training corpus (e.g. t + h) and merge it into a new token th.
  3. Repeat tens of thousands of times: th+e → the, ␣+the → ␣the …
  4. Stop at the target vocabulary size (typically ~32k–200k tokens). At inference time, the same merges are applied to your text.

Consequences you can observe

EffectWhy
English ≈ 3–4 characters per token. Code, JSON, and many non-English languages use more tokens per word.The vocabulary was built mostly from frequent English patterns
Limits and pricing are in tokens (context window, max_tokens, $ per million tokens)The token is the model's unit of work
Models can struggle to count letters ("how many r's in strawberry?") or reverse stringsThe model sees straw|berry as chunks, not individual characters
Arithmetic on long numbers can be shakyNumbers are split into irregular chunks
Different models give different token counts for the same textEach model family has its own tokenizer. Use the API's token-counting endpoint, or usage in responses, for exact counts.

4. Step 3 — Embeddings: token IDs → vectors

A token ID like 4881 is just an index. The model's first layer is an embedding matrix of shape [vocab_size × d_model]. Each token ID selects one row, and that row is the token's embedding vector.

vocab_size = 50,257   d_model = 768          # GPT-2 small (public numbers)
E = embedding matrix, shape [50257 × 768]   # learned during training

" France" → id 4881 → E[4881] = [ 0.021, -0.113, 0.487, …, 0.064 ]   # 768 numbers

Prompt of 5 tokens → matrix X of shape [5 × 768]
  • "Embedding" and "vector" are the same thing here. An embedding is a vector (a list of numbers). "Tokens → embeddings → vectors" is really one step: tokens → embedding vectors.
  • The values aren't hand-designed. They're learned in training, so tokens used in similar contexts end up with similar vectors (" Paris" near " Lyon", " king" near " queen").
  • Individual dimensions usually don't mean anything readable. Meaning is spread across many dimensions.
  • At this point each vector knows only which token it is, not its position or context. " bank" has the same starting vector in "river bank" and "bank account". The transformer layers fix that.

⚠️ Don't confuse the two kinds of "embeddings"
  • Token embeddings (this step): internal to the LLM, one vector per token, the input to the transformer.
  • Text embeddings for search/RAG: a separate embedding model (e.g. Voyage AI) turns a whole sentence or document into one vector. Similar meaning gives a high cosine similarity. These vectors go in a vector database for retrieval. The LLM never sees them; it only sees the retrieved text placed into the prompt.

5. Step 4 — Adding position

Attention (next step) is order-blind on its own. "dog bites man" and "man bites dog" would look identical. Models inject position information:

MethodHowUsed by
Sinusoidal (absolute)Add a fixed sine/cosine pattern per position to each embeddingOriginal Transformer (2017)
Learned absoluteAdd a learned vector per position (position 0, 1, 2 …)GPT-2
RoPE (rotary)Rotate the query and key vectors by an angle proportional to position. Attention then depends on relative distance.Llama and most modern LLMs

How position is encoded also limits how long a context the model handles well. Extending context windows mostly comes down to positional-encoding tricks plus training on long documents.

6. Step 5a — Self-attention: tokens share information

Self-attention lets every token look at earlier tokens and pull in relevant information. It's how " it" in "The animal didn't cross the street because it was too tired" picks up meaning from " animal".

Query, Key, Value

From each token's vector x, the layer computes three new vectors using learned weight matrices:

  • Query q = x·WQ: "what am I looking for?"
  • Key k = x·WK: "what do I contain?"
  • Value v = x·WV: "what will I hand over if you attend to me?"
Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k  +  causal_mask ) · V

1. Score:     each query · every key        → how relevant is token j to token i?
2. Scale:     ÷ √d_k                        → keeps softmax from saturating
3. Mask:      −∞ for future positions       → token i may only see tokens ≤ i  (causal)
4. Softmax:   scores → weights summing to 1
5. Mix:       weighted sum of value vectors → the new information for token i
Attention weights for " it" (illustrative)Weight
The0.02
animal0.61
didn't cross0.08
the street0.14
because0.05
it (itself)0.10
  • Causal mask: a token can't attend to future tokens. That's what makes the model a next-token predictor, and it's why generation goes left to right.
  • Multi-head: the layer runs many attention "heads" in parallel (e.g. 32), each with its own WQ, WK, WV. Different heads learn different relationships: syntax, coreference, copying, and so on. Their outputs are concatenated and projected back to d_model.
  • Cost: every token is compared with every earlier token, so attention compute grows quadratically with sequence length (O(n²)). Long contexts are expensive.
💡 Connects to "lost in the middle"Attention is a learned, soft weighting, not perfect lookup. In very long prompts, models tend to use information at the start and end more reliably than in the middle. That's why you put key instructions and facts at the beginning or end, under clear headers.

7. Step 5b — The transformer block, stacked N times

  • MLP (feed-forward network): applied to each token's vector independently. It expands to roughly 4× width, applies a non-linearity, and projects back. Most of a model's parameters, and much of its "factual knowledge", live here.
  • Residual stream: each sub-layer adds its output to the running vector rather than replacing it. Think of the vector as a shared workspace that every layer reads from and writes to.
  • Layer norm keeps the numbers in a stable range so deep stacks train well.
  • Depth builds meaning: early layers handle syntax and local patterns; middle and late layers handle meaning, facts, and the plan for the next token. By the last layer, the vector at the final position encodes "what should come next".
  • Mixture-of-Experts (MoE) variants replace the single MLP with many expert MLPs and a router that sends each token to a few of them. That gives more total parameters at similar compute per token.

8. Step 6 — Final vector → logits → probabilities

After the last layer, take the vector at the last position (the token right before the one being predicted). Multiply it by the unembedding matrix [d_model × vocab_size] to get one raw score, or logit, per vocabulary token.

h_last            shape [4096]
logits = h_last · W_U          shape [vocab_size]   e.g. 128,256 scores
probs  = softmax(logits / T)   all positive, sum to 1

For "The capital of France is", the top of the distribution might look like this:

The model doesn't output an answer. It outputs a distribution. Picking from it is a separate step.

Determinism caveatLow temperature makes outputs much more consistent, but even temperature 0 isn't strictly guaranteed to be bit-for-bit identical across calls on large-scale serving infrastructure. For reliability, design for validation and retries rather than assuming identical outputs.

10. Step 8 — The generation loop, KV cache, prefill vs decode

One forward pass produces one token. To write a reply, the model loops:

tokens = tokenize(prompt)
while True:
    probs = model(tokens)[-1]          # distribution for the next position
    nxt   = sample(probs, T, top_p)
    if nxt == END_OF_TURN or hit_stop_sequence or len(out) == max_tokens: break
    tokens.append(nxt); out.append(nxt)
    stream(detokenize(nxt))            # this is why responses stream word by word

KV cache

The keys and values for earlier tokens don't change when a new token is added, because of the causal mask. The server caches them, so each new step only computes Q, K, and V for the single new token and attends over the cache. Without it, every step would reprocess the whole sequence.

Two phases with very different performance

PhaseWhat happensDetermines
PrefillAll input tokens are processed in parallel in one pass, and the KV cache is filledTime to first token (TTFT). Grows with prompt length.
DecodeOutput tokens are generated one at a time, sequentiallyTokens per second. Total time grows with output length.
  • This is why output tokens cost more than input tokens: each needs its own sequential pass.
  • Prompt caching stores the processed state (KV cache) of a stable prefix (tools, system prompt, long documents). Later requests that start with the exact same prefix skip that prefill work, so they're faster and the cached tokens are billed at a much lower rate. Put static content first and changing content last.
  • Extended thinking is the same loop: the model generates reasoning tokens before the answer. They're real output tokens, so they cost time and money and use up the token budget.

11. Step 9 — Stopping, and where stop_reason comes from

What happened during generationAPI stop_reason
The model sampled its special end-of-turn tokenend_turn
The generated text matched one of your stop_sequencesstop_sequence
Output reached the max_tokens limit you set (text cut mid-thought)max_tokens
The model emitted a complete tool-call block and ended its turntool_use
The prompt plus output hit the model's context windowmodel_context_window_exceeded

So stop_reason isn't something the model "decides to say". It's the server reporting which stop condition fired. Your agent loop branches on it (see the agentic loop).

12. Step 10 — Detokenizing, streaming and tool calls

  • Detokenization: token IDs are mapped back to their byte sequences and joined into text. Because a multi-byte character can be split across tokens, streaming clients buffer partial bytes.
  • Streaming (server-sent events) sends each chunk as it's decoded. That's purely a delivery choice; the model computes the same way either way.
  • Tool use: the model was trained to emit a special structured format when it wants a tool. The API parses that into a tool_use content block (name, input JSON, id). The model never runs anything. Your code (or Claude Code's harness) executes the tool, and the result goes back into the next prompt as a tool_result, which is tokenized like any other text.
  • Structured output: a schema plus constrained decoding guarantees valid shape. Whether the values are correct still depends on the model, so validate the semantics.

14. Where the weights come from (training, briefly)

  1. Pre-training: the model reads trillions of tokens and learns to predict the next token. The error (cross-entropy loss) is pushed back through the network (backpropagation), nudging every weight: embeddings, attention matrices, MLPs, unembedding. This is where language, facts, and reasoning patterns come from.
  2. Post-training: supervised fine-tuning on high-quality conversations, then reinforcement learning from human and AI feedback (Anthropic uses techniques such as Constitutional AI). This turns a text predictor into a helpful, honest, harmless assistant that follows the chat format, uses tools, and knows when to stop.
  3. Inference (your API call): weights are frozen. Nothing in your prompt changes the model. "Learning" from examples in the prompt (in-context learning, few-shot) happens only within that context window and is gone on the next call.
Knowledge cutoffThe model only "knows" what was in its training data up to a cutoff date. Anything newer, or private, must come in through the prompt: retrieval (RAG), tool calls, MCP, or documents you attach.

"The model reads words or characters"It reads sub-word tokensBudget in tokens. Expect weak letter counting.

16. Self-check quiz

Score: 0 / 0 answered (of 8)

1 · What is a token embedding?
B. The ID is just an index (A). C describes text embeddings used for RAG, which are a separate model. D describes the output distribution.
2 · Why does a long conversation get slower and more expensive with every turn, even when your new message is short?
D. Every request resends the full conversation as input tokens. Prompt caching and compaction exist to reduce this cost.
3 · In self-attention, what does the causal mask do?
A. Future positions are set to −∞ before the softmax, which makes the model a left-to-right next-token predictor. C describes top-k/top-p.
4 · You set temperature very low. What happens?
C. Temperature only reshapes the softmax. The computation and the model's knowledge are unchanged, so correctness isn't guaranteed.
5 · A response ends with stop_reason: "max_tokens". What does that tell you?
B. The decode loop hit the max_tokens stop condition before the end-of-turn token was sampled.
6 · Why does prompt caching require the cached content to be at the start of the prompt?
D. Because of causal attention, changing an early token changes the state of every later token. An identical prefix gives identical KV state that can be reused.
7 · Why are output tokens slower and pricier than input tokens?
A. Decode is sequential, with one forward pass per token, while prefill handles the whole prompt at once.
8 · In a RAG system, how does the LLM use the vector database?
C. Retrieval happens outside the model. The LLM only sees the retrieved text, tokenized like the rest of the prompt.
