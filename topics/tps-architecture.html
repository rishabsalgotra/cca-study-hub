Topic 8 · Enterprise architecture

Designing for 1,000 TPS Without Building for 1 Million

An interactive architecture whiteboard for engineering leadership and application owners. It shows how an existing Amazon API Gateway + AWS Lambda platform can sustain 1,000 transactions per second when the real constraint is the downstream systems, and why that does not call for blockchain-style sharding or a massive distributed compute layer.

Animations follow your system's reduced-motion setting until you choose otherwise. Every diagram works without animation.

A. Executive overview

"TPS" hides three different numbers. Most throughput incidents happen because a team measured one of them and assumed the other two.

Ingress throughput

How quickly requests can enter the platform: API Gateway, authentication, validation, enqueueing. Managed AWS services usually make this the easiest number to raise.

Processing throughput

How quickly transactions are completed end to end, including every downstream call. It's bounded by the slowest required step, often a legacy system.

Sustainable throughput

The rate the whole system can run at indefinitely while still meeting its latency, availability and data-integrity requirements. This is the number to design and test for.

“Scale the ingress independently, control the processing rate, and remove or isolate downstream bottlenecks. A queue absorbs bursts; it does not create processing capacity.”

What 1,000 TPS means in practice

  • 86.4 million transactions per day at a sustained rate, or a much shorter peak window.
  • With 200 ms average processing time, about 200 transactions are in flight at any moment (Little's law: in-flight = rate × time).
  • If the legacy core sustains 300 TPS, no amount of Lambda concurrency completes 1,000 TPS of core-bound work. You must reduce, isolate, batch or partition that work.

The board-level answer

  • Keep API Gateway + Lambda for ingress. It is not the bottleneck.
  • Add durable queues, capped workers and downstream-specific adapters, so each system receives only what it can absorb.
  • Make async the default where the business contract allows it; keep a bounded, protected sync path where it doesn't.
  • Invest in idempotency, status tracking and reconciliation. That is where correctness lives.

What you're seeing: 1K buffered architecture

  • Bursts arrive faster than the API's rate limit, so some requests are throttled with 429 at the edge: backpressure working as designed.
  • Accepted requests are buffered in one queue per downstream. Watch queue A grow during bursts and drain afterwards: the queue absorbs the burst, it doesn't speed anything up.
  • Each worker pool has a fixed cap (2, 3, 2), so the slow legacy core never sees more than 2 concurrent calls.
  • Partner failures retry after a visibility timeout. After 3 attempts the message is dead-lettered instead of blocking the lane.
  • Lane C's problems never slow lanes A and B: queue isolation and bulkheads.

What you're seeing: 1M sharded architecture

  • A high, uniform stream of transactions is routed to the shard that owns each sender account.
  • All six shards execute in parallel, so throughput grows with the number of shards.
  • About half the transactions produce a cross-shard receipt that executes on the receiver's shard: the coordination cost of partitioning.
  • Results pass through consensus before being finalized.
  • Nothing here waits on an external legacy system, which is precisely why this model doesn't transfer to the enterprise case.

Why the difference matters

The 1M design gets throughput by adding parallel owners of state. The 1K design gets safe throughput by pacing work to fixed-capacity owners of state. If you can't partition the system of record, more parallelism just moves the queue into the legacy system, where it shows up as timeouts.

Model and assumptions (read before quoting any number)

Notation: λ = incoming TPS during the burst, λ₂ = arrival rate after it, T = burst duration, t = average processing time (s), N = worker concurrency, Dᵢ = sustainable capacity of downstream i, mᵢ = traffic share of branch i.

Worker capacity (TPS) W = N / t Concurrency in flight L = λ × t (Little's law) Branch arrival rate aᵢ = λ × mᵢ Serial chain capacity C = min(W, D_A, D_B, D_C) (every stage is required) Independent branches Cᵢ computed separately per branch (never multiplied into one chain) Queue growth rate g = max(0, accepted − completed) Queue depth after the burst Qᵢ = max(0, Q₀·mᵢ + (aᵢ − Cᵢ) × T) Drain time after the burst Qᵢ / (Cᵢ − λ₂·mᵢ) (∞ if Cᵢ ≤ λ₂·mᵢ)
  • 1 · Synchronous: each branch completes min(aᵢ, Dᵢ). Excess requests wait up to the timeout before failing, holding concurrency: demand = Σ completedᵢ·t + Σ excessᵢ·timeout. If demand exceeds N, every branch is scaled by N ÷ demand. This is how one slow system starves healthy ones in a shared synchronous pool. Accepted = completed; nothing is buffered.
  • 2 · Async, shared queue and workers: work advances in mix proportion, so capacity C = min(W, minᵢ Dᵢ ÷ mᵢ) (head-of-line blocking). Without per-downstream limits, workers offer W × mᵢ to each system while a backlog exists; above 100% that means errors and retries.
  • 3 · Per-downstream limits: concurrency is budgeted per system, demand first: baseᵢ = min(Dᵢ, aᵢ) × t (shared in proportion if N is too small). Any spare concurrency goes to systems that can use it to drain backlog, up to Dᵢ × t. Then Wᵢ = budgetᵢ ÷ t and Cᵢ = min(Dᵢ, Wᵢ). Offered load never exceeds Dᵢ.
  • 4 · Parallelized: as option 3, with Dᵢ multiplied by the partition count only for systems you mark as partitionable.
  • Rates are steady-state averages: no warm-up, cold starts, latency distributions, retries' extra load, or service quotas. Accepting faster than you complete assumes your buffer, message retention and API acceptance contract (202) allow it.
  • Charts integrate the same rates over time (240 steps); the time axis is capped at one hour after the burst.

E. Protecting non-scalable downstream systems

Getting to 1,000 TPS safely means making every layer respect the capacity of the slowest system it depends on. These fourteen controls work together. Open a card for where it belongs, when it helps, its limitations, and its effect on latency, throughput and reliability.

Exactly-once is an application property, not a broker featureSQS Standard delivers at least once. FIFO deduplication only removes duplicate messages sent within its deduplication window. Lambda retries, timeouts and partial batch failures can still invoke your code more than once. Exactly-once business effects (one debit per payment) require application-level idempotency keys, conditional writes or transactions, and reconciliation for ambiguous outcomes. No message broker guarantees them on its own.
Show:
1BackpressureStop upstream systems from generating unlimited work
Problem it solves
Producers can create work faster than it can be completed, which leads to unbounded queues, rising latency and eventually failure.
Where it belongs
At the API edge (429/503 with Retry-After), in the ingress Lambda (refuse new work when queue age exceeds the acceptance SLA), and between internal stages.
When it is useful
Whenever acceptance can outrun completion, which is always true for buffered designs.
Limitations
It moves the problem to callers, who must honour Retry-After with backoff and jitter. It needs a reliable saturation signal (queue age is better than depth).
Effect
Latency: protects p99 of accepted workThroughput: deliberately caps acceptanceReliability: ↑ prevents collapse
2Rate limitingEnforce sustainable rates globally and per downstream
Problem it solves
Demand above what a system can sustain, and noisy clients consuming a shared budget.
Where it belongs
API Gateway throttling and usage plans (per client and route); a token bucket in each downstream adapter (per system).
When it is useful
Always for legacy and partner systems with known or contracted capacity.
Limitations
Per-instance limiters multiply as workers scale out, so you need a shared limiter or a concurrency cap. Static limits drift from real capacity, so revisit them after every capacity test.
Effect
Latency: ↑ for queued workThroughput: capped at the safe rateReliability: ↑
3Concurrency limitsControl simultaneous calls into legacy systems
Problem it solves
Too many parallel calls exhaust connection pools, sessions or threads in the legacy system.
Where it belongs
The SQS event source mapping's maximum concurrency per queue, Lambda reserved concurrency, and adapter connection pools.
When it is useful
For systems with fixed connection limits. It is self-correcting: if the system slows down, rate = concurrency ÷ latency falls automatically.
Limitations
Concurrency isn't rate. Set it too low and you waste capacity; too high and it doesn't protect anything. Size it from Little's law and measured latency.
Effect

Problem it solves
Head-of-line blocking: with one shared queue, messages for a slow or failing system occupy workers and delay everything else.
Where it belongs
One queue (and DLQ) per downstream or per transaction class, routed by the ingress or EventBridge rules.
When it is useful
Mixed workloads with different capacities, SLAs or failure rates. Compare options 2 and 3 in the simulator.
Limitations
More queues to operate and monitor; no ordering guarantees across queues; routing logic must stay correct.

Problem it solves
Per-call overhead (connection, authentication, commit) dominates, so the system spends its capacity on ceremony.
Where it belongs
SQS batch receive (batch size and batching window), plus an adapter that aggregates items into the backend's bulk API.
When it is useful
Only when the backend genuinely supports bulk operations and the latency budget allows a short wait.

Partial failures are complex (use ReportBatchItemFailures). The batching window adds latency, and a failed call affects many transactions.

6IdempotencyPrevent duplicate business operations during retries
Problem it solves
At-least-once delivery, client retries and Lambda retries can otherwise post the same payment twice.
Where it belongs
The API (Idempotency-Key header); ingress (conditional write of the key); the worker before the downstream call; and the downstream itself when it accepts an idempotency reference.
When it is useful
Always, for every state-changing operation.
Limitations
Needs a durable key store with a TTL and a defined answer for "same key, different payload". It can't make a non-idempotent downstream safe on its own, so you also need reconciliation.
Effect

7Dead-letter queuesIsolate repeatedly failing messages
Problem it solves
Poison messages retry forever, wasting worker and downstream capacity and hiding real failures.
Where it belongs
A redrive policy on every SQS queue (maxReceiveCount); on-failure destinations for async Lambda invocations.
When it is useful
Always for asynchronous processing.
Limitations
A DLQ is a parking lot, not a fix. It needs alarms, triage runbooks and a redrive process. Dead-lettering breaks ordering, and messages still expire at the retention limit.

On every remote call, and especially on synchronous paths.

Separate functions or event source mappings with their own concurrency, separate connection pools, separate API keys and quotas, and separate sync and async capacity.
When it is useful
When there are several dependencies with different reliability, and whenever sync and async traffic share infrastructure.

Reserved capacity can sit idle, and there is more configuration to maintain.

The differences that matter

Accepted ≠ processed ≠ completed

Accepted: durably recorded and queued (HTTP 202). Processed: a worker attempted it. Completed: the downstream confirmed the business effect. Report all three. Ingress dashboards that show only "accepted" hide a growing backlog.

Retries happen at three layers

Clients retry, the SDK retries, and SQS redelivers. Uncoordinated, they multiply load during an incident. Pick one owner for business retries (the queue), cap the others, and make every layer idempotent.

Reserved concurrency vs maximum concurrency

Lambda reserved concurrency guarantees and caps a function's share of the regional pool. Event source mapping maximum concurrency caps how many concurrent invocations one SQS queue drives, so you can protect a downstream without throttling the function itself.

G. Synchronous vs asynchronous API contracts

Not every transaction can be asynchronous. A real-time authorisation, a balance check before a trade, or an instant-payment confirmation needs a definitive answer now, and it stays synchronous unless the business contract changes. Everything else should default to async.

Asynchronous: accept, then complete

POST /v1/payments Idempotency-Key: 7f3c9a2e-1b4d-4e88-9c1a-52d0e6a1b9f4 { "debtor": "ACC-1001", "amount": "2500.00", "currency": "EUR" } HTTP/1.1 202 Accepted Location: /v1/payments/txn_01HZX4Q8 { "correlationId": "txn_01HZX4Q8", "status": "ACCEPTED" } GET /v1/payments/txn_01HZX4Q8 HTTP/1.1 200 OK { "status": "SUCCEEDED", "completedAt": "2026-10-12T09:41:07Z" }

202 means "durably recorded and queued", nothing more. Repeating the POST with the same key returns the same correlation ID instead of creating a second payment.

Synchronous: bounded wait, explicit overload

POST /v1/authorisations Idempotency-Key: 0b5e… (client timeout: 3 s) HTTP/1.1 200 OK ← answered within the bound HTTP/1.1 429 Too Many Requests Retry-After: 2 ← over quota: shed early, cheaply HTTP/1.1 503 Service Unavailable Retry-After: 5 ← breaker open / downstream saturated HTTP/1.1 504 Gateway Timeout ← outcome UNKNOWN: reconcile, don't blindly retry

Fail fast with 429/503 rather than letting requests queue until they time out. A 504 after the request was sent is an ambiguous outcome: retry only with the same idempotency key, and reconcile.

How to actually prove 1,000 TPS

  1. Measure each downstream aloneFind each system's sustainable TPS and latency curve, and the point where latency turns non-linear, in a production-like environment, with the owners' agreement.
  2. Set budgets from measurementsPer-downstream rate limits and concurrency = measured sustainable capacity minus safety headroom (e.g. 20–30%).
  3. Check AWS quotasRegional Lambda concurrency, API Gateway throttles, and SQS/FIFO throughput for your exact configuration. Request increases before the test, not during it.
  4. Load test end to endRamp to 1,000 TPS with a realistic transaction mix, then hold it long enough to see steady state, then run bursts above it.
  5. Test the failure modesSlow one downstream, fail another, and confirm isolation, DLQ behaviour, alarms and reconciliation.
  6. Record the result as a measured numberOnly now does "1,000 TPS" stop being a design target.

I. Recommendation and roadmap

Keep the existing API Gateway + Lambda platform. Reach 1,000 TPS by buffering asynchronous work, pacing each downstream to its measured capacity, protecting the synchronous path, and making every transaction idempotent and traceable. Reserve sharding-style redesigns for workloads you own end to end and that genuinely need far more than a few thousand TPS.

Self-check quiz

Score: 0 / 0 answered

1 · The legacy core sustains 300 TPS. You add an SQS queue in front of it and accept 1,000 TPS of core-bound traffic for an hour. What happens?
C. A queue absorbs bursts; it doesn't create processing capacity. Sustained arrivals above capacity just grow the backlog (about 2.5 million messages after an hour).
2 · Which control most directly prevents a slow partner API from delaying legacy-core transactions?
B. Isolation stops head-of-line blocking and resource starvation. Compare simulator options 2 and 3 at the same load.
3 · With 250 concurrent workers and 200 ms average processing time, what is the worker capacity?
D. Capacity = concurrency ÷ time = 250 ÷ 0.2 s = 1,250 TPS. Whether that is usable still depends on each downstream's capacity.
4 · A worker times out calling the core after sending a payment. What is the correct handling?
A. A timeout after sending is an ambiguous outcome. Guessing either way risks a duplicate payment or a lost one.
5 · Does SQS FIFO give you exactly-once business effects?
C. Exactly-once business effects are an application property built on idempotency keys, conditional writes and reconciliation.
6 · Why isn't the NEAR 1M TPS benchmark a template for an enterprise API that calls legacy banking systems?
B. Different constraint, different solution: sharding helps when you own partitionable state; pacing and protection help when the bottleneck is downstream.
